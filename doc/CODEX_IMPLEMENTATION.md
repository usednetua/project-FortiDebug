# Кодекс впровадження

**Статус:** обов’язковий для всіх агентів і розробників проекту FortiDebug Builder.  
**Джерело правил агента:** `AGENTS.md` (локально / project instructions).

Цей кодекс визначає мінімальний процес перед і під час будь-якого впровадження функціоналу, рефакторингу чи змін у коді.

---

## 1. План перед впровадженням

Перед початком впровадження **будь-чого** (нова фіча, recipe, CI, UI-вкладка, виправлення з ризиком регресії) обов’язково:

1. Створити **детальний покроковий план** у вигляді файлу в папці `doc/`.
2. Ім’я файлу:
   - реліз / великий обсяг: `doc/RELEASE_N_PLAN.md`
   - окрема фіча / задача: `doc/FEATURE_<коротка_назва>_PLAN.md`
   - кодекс / процес (цей файл): `doc/CODEX_*.md`
3. План має бути достатньо детальним, щоб інший розробник або агент міг виконати роботу без додаткових уточнень щодо порядку кроків.

**Заборонено** починати писати код або пушити зміни без такого плану (окрім тривіальних правок: опечатка, один рядок CHANGELOG, косметика README — за згодою / явним запитом).

---

## 2. Таблиця етапів на початку плану

На **початку** кожного плану обов’язково є таблиця зі всіма етапами:

| # | Крок | Стан | Пріоритет | Примітки |
|---|------|------|-----------|----------|
| 1 | … | ⬜ Todo / 🔄 In progress / ✅ Done | P0 / P1 / P2 | … |

Правила:

- Стан оновлюється після завершення кроку.
- Пріоритет: **P0** — блокує реліз / критично; **P1** — важливо; **P2** — можна відкласти.
- У примітках — залежності, ризики, посилання на файли / коміти.

Приклад (фрагмент):

| # | Крок | Стан | Пріоритет | Примітки |
|---|------|------|-----------|----------|
| 1 | Описати scope у CHANGELOG [Unreleased] | ✅ Done | P0 | |
| 2 | Додати recipe ZTNA (version-aware) | ✅ Done | P0 | `recipe_extra.py` |
| 3 | Regression: Sessions / Sniffer / Flows | ⬜ Todo | P0 | «не зламай!» |

---

## 3. Перевірка після кожного етапу («не зламай!»)

Після опрацювання **кожного** етапу обов’язково:

1. Перевірити **весь зачеплений функціонал** і сумісність з уже робочими частинами.
2. Мінімальний чеклист (адаптувати під задачу):
   - [ ] Модуль / вкладка відкривається без traceback
   - [ ] Генерація команд для типового сценарію коректна
   - [ ] Version-aware синтаксис (якщо є FortiOS selector) не зламаний для 6.x / 7.x / 8.x
   - [ ] Існуючі recipes / tabs, які використовують ті самі helpers, не регресують
   - [ ] `pytest` (якщо є тести на змінений код) — зелені
   - [ ] CHANGELOG оновлено **перед** комітом (див. правило агента)
   - [ ] Перед релізом: згенеровано `RELEASE_NOTES.md` (див. `AGENTS.md` §3)
3. Якщо перевірка виявила регресію — **спочатку виправити**, потім позначати етап ✅ Done.
4. У таблиці плану в «Примітки» коротко зафіксувати результат перевірки (або «N/A» + причина).

Принцип: **краще відкласти наступний етап, ніж залишити зламаний попередній.**

---

## 4. Зв’язок з іншими правилами

| Правило | Де |
|---------|-----|
| Завжди записувати зміни в `CHANGELOG.md` **перед** комітом | `AGENTS.md` §1 |
| Кодекс впровадження (цей документ) | `doc/CODEX_IMPLEMENTATION.md` + `AGENTS.md` §2 |
| **`RELEASE_NOTES.md` під кожен реліз + публікація з GitHub Release** | `AGENTS.md` §3, CI `build-windows.yml` |
| Плани релізів | `doc/RELEASE_*_PLAN.md`, `doc/PLAN.md` |
| Індекс документації | `doc/INDEX.md` (оновлювати при зміні `doc/`) |
